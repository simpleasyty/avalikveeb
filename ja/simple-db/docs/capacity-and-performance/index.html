保存とプライバシー

容量、制限、測定されたパフォーマンス

確認済みの Forge 制限、アプリの保護上限、SQL インポートの測定結果に基づき Simple DB の負荷を計画します。

検証結果から分かること

確認日：2026年11月26日。プラットフォームの上限、アプリの保護上限、実測の性能はそれぞれ異なります。インポートの成功だけでは、対応する最大データベース容量や同時利用者数は証明できません。

Forge トンネルを使用した Confluence development の実環境インポート1回で、100,000行の完全性を検証しました。追加のローカル試験3回では、準備処理と模擬バッチ実行を確認しました。同時実行、本番スループット、サービスレベルのパーセンタイルは未検証です。

KVS と呼び出しの予算

Atlassian は KVS の値1件につき240 KiB、毎秒1,000件の KVS リクエスト、読み取りと書き込みそれぞれ毎分4,000単位を定めています。サイズは10 KB単位で切り上げられるため、リクエスト件数だけではストレージ利用量を表せません。

フロントエンドの invoke リクエスト上限は500 KBです。SQL、KVS、呼び出しの予算を合わせて検討する必要があります。いずれもブラウザーの描画能力を示すものではありません。

Simple DB インポートの保護上限

以下はインポート実装の上限です。元のファイルが32 MiB未満でも、準備された JSON が予算を超える場合があります。同時アップロード3件は、SQL の同時実行3件や同時利用者3人を意味しません。

  • 大きな単純形式の INSERT INTO … VALUES は分割できますが、任意の大きな SQL を分割できるわけではありません。
  • 文は順番に実行され、最初のエラーで停止します。それまでに確定した変更は残ります。
  • チェックポイントは短いバッチを目指す設定であり、8秒ごとの画面更新保証ではありません。確定とチェックポイント保存の間でプラットフォームが中断すると結果が不確定になることがあります。非冪等スクリプトを無条件に再実行しないでください。

実環境インポートの測定結果

2026年11月26日の1回の試験では、Forge トンネル経由の Confluence development を使用しました。SQL ファイルは14,534,889バイト、アップロードは125分割で、CREATE が1文、各100行の INSERT が1,000文でした。

測定区間はプロセスをキューに登録してから Completed になるまでです。待機と実行を含み、アップロードと準備は含みません。並列アップロードと短いチェックポイントを導入する前の実装であり、後から加えた最適化のベンチマークではありません。

  • 引用符、カンマ、セミコロンを含む保存値を3レコードで確認しました。
  • 検証後、専用のテストテーブルを削除しました。
  • これらは1回の試験から算出した平均であり、ピーク値、p95 レイテンシ、実際の SQL API 呼び出し件数ではありません。カタログと権限確認の処理は個別に計測していません。この値を150 RPSで割って未使用容量を推定することはできません。

ローカルの再現性：3回の試験

各試験ではApple M4、16 GiB RAM、macOS、Node.js v22.16.0 のワークステーション1台で現在のインポートプランナー、模擬 SQL、メモリー内 KVS を使用しました。表の時間は準備処理のみのミリ秒値です。MiB 表記は生成した負荷の概算で、正確な SQL バイト数を併記しています。実際のデータベース書き込み速度ではありません。

  • 3回のスイートはすべて成功しました。各7シナリオ、合計21シナリオ実行です。
  • 各チェックポイント模擬試験は9,381文を470バッチで完了し、文の欠落と重複はありませんでした。
  • サイズ超過、途中で切れた入力、過剰な文数、失敗後に実行をキュー登録しないアップロードを確認しました。模擬実行速度を Forge SQL のスループットとして扱うことはできません。

再現と完全性の確認

本番以外の専用インストールと固有名のテストテーブルを使います。アプリのリビジョン、デプロイ方法、ファイルサイズ、行の幅、インデックス、文数、INSERT ごとの行数、空き容量、同時ジョブ数を記録します。

準備、アップロード、待機、実行を別々に測定します。SQL で結果と代表的な値を検証し、試験で作成したテーブルだけを削除します。整数 ID が1～100,000なら、行数100,000、一意の ID 数100,000、チェックサム5,000,050,000が期待値です。

SELECT COUNT(*) AS row_count,
       COUNT(DISTINCT id) AS unique_ids,
       MIN(id) AS min_id, MAX(id) AS max_id,
       SUM(id) AS id_sum
FROM your_isolated_test_table;

対応規模を表明する前に

トンネルを使わないデプロイ済み環境で1、14、32 MiBを試し、同一インストール内で権限のある別々のアカウントを使い、同時ジョブ数1、3、5でも繰り返します。10回連続インポート、書き込み中の通常読み取り、キャンセル、ブラウザー終了、スロットリング、実行中断も検証します。

負荷ごとの応答時間と完了時間の目標を試験前に定めます。試行数、p50/p95、エラーとスロットリングの比率、完全性、クエリ時間予算、KVS と呼び出しの利用量を公開します。反復時の公平性とリソースの安定性も確認します。

これらの実環境での同時実行・耐久試験は未実施です。現在説明できるのは、開発環境で100,000行のインポート1回が正しく完了したことです。同時インポート容量や本番 SLA は表明していません。
