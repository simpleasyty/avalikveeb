Capacity, limits and measured performance

Plan Simple DB workloads using verified Forge limits, application safeguards and measured SQL import results.

What the evidence supports

Checked on 26 November 2026. Platform ceilings, application safeguards and observed performance are different measurements. A successful import does not establish the maximum supported database size or number of concurrent users.

One live Confluence development import through the Forge tunnel completed 100,000 rows with exact integrity checks. Three additional local runs checked preparation and simulated batch execution. Concurrent live imports, production throughput and service-level percentiles have not been established.

KVS and invocation budgets

Atlassian documents 240 KiB per KVS value, 1,000 KVS requests per second, and separate read and write budgets of 4,000 units per minute. Payload sizes round up in 10 KB units; request counts alone do not describe storage usage.

Front-end invoke requests have a 500 KB ceiling. SQL, KVS and invocation budgets must all be considered; none measures browser rendering capacity.

Simple DB import safeguards

These bounds come from the import implementation. A file can hit the prepared JSON budget before its original file size reaches 32 MiB. Three simultaneous upload requests do not mean three simultaneous SQL executions or three supported users.

  • Plain oversized INSERT INTO … VALUES statements can be divided; arbitrary large SQL cannot.
  • Statements execute in order. The first error stops the import; earlier changes remain committed.
  • Checkpoints target short batches, not an eight-second UI refresh guarantee. A platform interruption between commit and checkpoint can leave an uncertain result; do not blindly replay a non-idempotent script.

Live import: measured result

One run on 26 November 2026 used Confluence development with the Forge tunnel: a 14,534,889-byte SQL file, 125 uploaded parts, one CREATE and 1,000 INSERT statements of 100 rows each.

The measured window starts when the process was enqueued and ends at Completed. It includes queueing and execution, excludes file upload and preparation, and used the implementation before parallel uploads and shorter checkpoints. It is not a benchmark of those later optimizations.

Reproduce and verify integrity

Use a dedicated non-production installation and uniquely named test tables. Record the app revision, deployment mode, file bytes, row width, indexes, statement count, rows per INSERT, available storage and number of simultaneous jobs.

Measure preparation, upload, queue wait and execution separately. Verify the result with SQL, inspect representative values and remove only the tables created by the test. For integer IDs 1–100,000, expect 100,000 rows, 100,000 distinct IDs and checksum 5,000,050,000.

SELECT COUNT(*) AS row_count,
       COUNT(DISTINCT id) AS unique_ids,
       MIN(id) AS min_id, MAX(id) AS max_id,
       SUM(id) AS id_sum
FROM your_isolated_test_table;

Before claiming a supported scale

Repeat deployed tests without the tunnel at 1, 14 and 32 MiB, then with one, three and five jobs sharing an installation, using distinct authorized accounts. Run ten successive imports, test normal reads during writes, and exercise cancellation, browser closure, throttling and interrupted execution.

Agree workload-specific latency and completion targets before testing. Publish sample counts, p50/p95 times, error and throttle rates, integrity results, query execution budget and KVS/invocation usage. Check fairness and resource stability across repeated runs.

These live concurrency and endurance tests are still pending. The defensible conclusion today is that one 100,000-row development import completed correctly; no simultaneous-import capacity or production SLA is claimed.
